# Atomic Drift Tuner v0.3 architecture

## Main tuning pipeline

`TuneInput -> TuningEngine -> TuneResult`

`TuneInput` contains:

- wheelbase
- steering wheel/rim
- drift pack
- car
- driver intent

The tuning engine generates AZOM/MOZA-oriented settings and Assetto Corsa FFB settings.

## Car validation

`AssettoCorsaScanner` attaches a `CarDataConfidence` object to each detected car.

Direct file sources can promote confidence:

- `ui_car.json`: mass/power when parseable
- `data/car.ini`: mass and plausible steering lock when unpacked
- `data/tyres.ini`: front tire width when unpacked

Pack-derived/default values remain low or medium confidence. The UI can mark edited values as user-verified.

## Calibration pipeline

`TuneInput + CalibrationFeedback -> CalibrationEngine -> CalibrationProfile`

A calibration profile is keyed by:

`Hardware.Id | Wheel.Id | DriftPack.Id | Car.Id`

This prevents feedback from leaking across unrelated combinations.

`TuningEngine.Generate(input, calibration)` applies bounded correction deltas after calculating the baseline recommendation.

## Calibration persistence

`CalibrationStore` saves profiles to Local App Data. It supports get, upsert, and delete operations.

Tune export can embed the active calibration so it can be moved to another PC/profile and restored on load.

## Future adapters

Direct integrations should remain separate from the tuning model:

- `IAzomAdapter`
- `IAssettoCorsaConfigAdapter`
- `IAssettoCorsaTelemetrySource`
- `ICarPhysicsReader`

The recommended next milestone is telemetry collection and analysis before one-click hardware writes.

## v0.3.1 Assetto Corsa car setup layer

`Saved AC setup .ini -> AssettoCorsaSetupService -> CarSetupAnalysis -> CarSetupTuningEngine -> new Atomic_*.ini`

The setup writer preserves all original lines except `VALUE=` entries in sections with accepted recommendations. The source/baseline file is never overwritten.

If `content/cars/<car>/data/setup.ini` is available, numeric MIN/MAX/STEP metadata is associated with saved-setup sections for clamping/snapping. Packed `data.acd` is not unpacked by this version.

## v0.4 telemetry pipeline

`Assetto Corsa acpmf_physics -> AssettoCorsaTelemetryReader -> TelemetrySession -> TelemetryAnalyzer -> TelemetryCalibrationSuggestion`

The telemetry source is intentionally read-only. The analyzer emits small deltas into the existing `CalibrationProfile`; it never writes directly to MOZA/AZOM or AC hardware/configuration.

Session data is saved separately from tune profiles so raw telemetry can be re-analyzed later when the algorithms improve.


## v0.4.1 Full AZOM model

`AzomSettings` is now composed of typed sections matching the AZOM Base page. Performance controls are generated by `TuningEngine`; preference controls come from `AzomUserPreferences` persisted in `AppSettings`. This separation prevents per-car tuning from toggling unrelated device preferences.

## v0.5 Live AZOM adapter

The main tuner remains independent of SimHub assemblies.

`AzomSettings -> AzomLiveController -> SimHubActionInvoker`

Read path:

`AZOM public properties -> Atomic SimHub Bridge (net48/x86) -> named pipe -> AzomBridgeClient -> comparison`

Write path:

`comparison -> action plan -> SimHubWPF.exe -triggeraction -> AZOM actions -> hardware -> bridge readback`

The optional bridge is kept outside the main solution so missing/updated SimHub SDK assemblies cannot break the normal tuner build.

## v0.5 theme architecture

All user-facing windows consume `DynamicResource` brushes. `ThemeService` changes only application resources; tuning engines and models have no dependency on it.

`ThemeSettings -> AppSettingsStore -> ThemeService -> WPF DynamicResource brushes`


## v0.6 UI isolation

Theme customization is applied only through WPF DynamicResources. The color
wheel writes ThemeSettings values; it never references tuning engines, car
profiles, telemetry, or AZOM commands.

## v0.6 live AZOM batch policy

`BuildPlan -> user selection -> exact commit -> live readback -> audit`

A batch never advances past an unverified setting. Revert uses the pre-apply
snapshot and the same verified write/readback loop.


## v0.6.1 Per-car desired behavior layer

The AC setup pipeline now accepts a `CarBehaviorTarget` in addition to the
session-level `DriftIntent` and `SetupAggressiveness`.

Persistence is intentionally separate from hardware calibration:
`CarBehaviorProfileStore` keys targets by drift pack + car and stores them in
`car-behavior-targets.json`. Wheelbase/wheel changes therefore do not change how
the user wants the car itself to behave.

`CarSetupTuningEngine` first calculates the existing intent-based setup delta,
then adds a smaller behavior-target delta. The final proposed value still passes
through the existing range/click-aware `SnapAndClamp` safety layer.


## v0.6.2 Behavior blending layer

Desired Behavior is now contribution-aware.

For each recognized AC setup parameter:

`behavior axes -> signed contributions -> same-direction damping / opposing-goal compromise -> session-intent priority -> SnapAndClamp`

Same-direction behavior contributions use diminishing returns. Opposing behavior
contributions cancel overlap and soften the remaining net request as conflict
strength rises.

After behavior-only blending, the engine compares the result with the existing
session-intent delta. If they oppose, the per-car behavior layer is reduced to
65% for that parameter so session intent remains the higher-level instruction.

`BehaviorBlendReport` records actual behavior conflicts, session-intent conflicts,
aligned stacks, affected parameters and a bounded audit list. `BlendStatus` is
stored per setup row for UI inspection.

`PreviewBehaviorBlend()` uses the same behavior-effect directions for the
recognized parameter groups to show likely compromises before Generate.

This layer does not bypass `SnapAndClamp`, does not change setup.ini compatibility
rules, and has no dependency on Live AZOM, telemetry, theme code or the SimHub
bridge.


## v0.6.3 Beta distribution layer

Machine-specific configuration is separated from tuning/profile data.

`AppSettings` now owns:
- `SimHubRoot`
- `AssettoCorsaRoot`
- `AssettoCorsaDocumentsRoot`
- `FirstRunCompleted`

The setup wizard uses `MachineConfigurationService` and `SimHubLocator`.
The AC setup service resolves its saved-setup root through configured AC user
data rather than constructing a fixed user Documents path.

`BridgeManagerService` treats the precompiled bridge as a release payload. It
will not build against tester machines. It only verifies SimHub, refuses writes
while SimHub is running, copies the payload, and optionally relaunches the same
Atomic executable with a narrow `--install-bridge` UAC helper command when
administrator access is required.

`SystemDiagnosticsService` is read-only except when the user explicitly exports
a support ZIP. Exported machine paths are redacted to `%USERPROFILE%` and
`%LOCALAPPDATA%`. User tuning/telemetry/setup data is excluded.

The release builder is intentionally outside the WPF project:
`distribution\build-beta-package.ps1`.

It produces:
- self-contained x64 Atomic application,
- precompiled bridge payload,
- portable ZIP,
- optional Inno Setup installer.


## v0.7.0 Telemetry-assisted tuning layer

The assistant is intentionally a review/orchestration layer instead of a second
independent tuning engine.

Flow:

`Saved telemetry + current TuneInput + saved CarBehaviorTarget`
`-> TelemetryTuningAssistantEngine`
`-> Desired-vs-observed assessments`
`-> preserve notes / bounded CalibrationSuggestion / temporary behavior target`
`-> user review`
`-> existing CalibrationEngine and/or existing CarSetupTuningEngine`

The assistant never directly writes AZOM and never writes an AC setup file.

`TelemetrySessionStore.ListRecent()` matches exact wheelbase + wheel + pack + car
sessions and supports older saved session JSON through case-insensitive parsing.

TelemetryAnalysis now also stores drift-only average wheel-slip summaries,
average absolute FFB, and the percentage of detected drift samples with
`abs(FinalFfb) >= 0.98`.

Measured axes in beta 1:
- transition speed,
- self-steer heuristic,
- extreme-angle/stability heuristic,
- oscillation clustering,
- FFB clipping/headroom.

Unisolated axes are deliberately surfaced as TARGET SAVED instead of receiving
automatic changes:
- front-end bite,
- rear grip,
- throttle steering,
- initiation sharpness.

Temporary car-setup guidance is implemented by passing an unsaved
`CarBehaviorTarget` override into `CarSetupWindow`; the existing behavior-blend
engine, setup.ini legal-range logic and non-overwrite policy remain authoritative.


## v0.7.3 modeless theme-editing safety

`ThemeWindow` is a modeless UI-only tool. Preview applies only
`Application.Current.Resources` through `ThemeService.Apply()`. Persisting a
theme changes only `AppSettings.Theme`.

MainWindow keeps one modeless instance per normal tool window. Post-close work
that previously ran after `ShowDialog()` now runs in each window's `Closed`
handler. This preserves calibration/preference refresh behavior without blocking
the theme editor.

Each modeless tuning window keeps the `TuneInput`/result snapshot supplied at
construction. Changing selections in MainWindow does not silently retarget an
already-open AZOM/AC-setup/telemetry window.

The first-run machine setup remains modal because valid machine paths are an
initialization prerequisite.
