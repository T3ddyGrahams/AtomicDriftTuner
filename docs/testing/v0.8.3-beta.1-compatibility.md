## Current evidence

The [release notes](../releases/v0.8.3-beta.1.md) document 156 layout assertions, 18 regression scenarios including an 8,000-combination range check, packaged launch, installer upgrade, preserved saved data, and maintainer acceptance of the UI preview.

Those results establish useful release checks. They do not establish how a particular wheelbase feels, live Apply/Revert compatibility, or complete display coverage. The maintainer's UI acceptance did not record all hardware and display details needed for a configuration entry below.

**No field-test configurations have been entered in this tracker yet.** The tables start empty so untested combinations cannot be mistaken for verified hardware. Results are reviewed and added manually; submitting an issue does not automatically update this file.

### Status meanings

| Status | Use when |
| --- | --- |
| Untested | No usable evidence exists for this configuration and area. |
| Partially Tested | Some evidence exists, but relevant cases or configuration details are still missing or blocked. |
| Community Verified | A tester provided the configuration, evidence, and passing results for every applicable case in the stated area; a maintainer reviewed the report. This is limited to that area. |
| Verified | A maintainer also reproduced the applicable passing cases on the stated configuration and recorded the evidence. This is limited to that area. |
| Known Issue | A reported failure affects the stated area. Link the bug and record whether it is reproduced or awaiting reproduction. Passing cases remain listed. |
| Unsupported | A maintainer has explicitly documented that the configuration or feature is unsupported, with a link explaining why. Lack of testing alone does not mean unsupported. |

"Not run" and "Blocked" are test outcomes, not passes. `N/A` needs a reason, such as no SimHub installed. Do not use skipped cases to verify a feature that was not exercised. A technically successful Apply/Revert does not establish that the recommended tune improved driving.

## Adding a report

1. The tester follows the [release checklist](v0.8.3-beta.1-checklist.md), records each attempted case, and submits the existing [Beta Test Report](https://github.com/T3ddyGrahams/AtomicDriftTuner/issues/new?template=beta_test_report.yml). Use the [Bug Report](https://github.com/T3ddyGrahams/AtomicDriftTuner/issues/new?template=bug_report.yml) for failures and link it from the test report.
2. The maintainer checks the ADT/build version, context, case results, and evidence. Ask for missing details only when needed to interpret the result; retain `Unknown` rather than guessing.
3. Add or reuse the environment row, then add results for each tested area. Link the original report and any related bug. Record the review date.
4. Update the coverage table with links to the relevant results/report. Preserve mixed results and failures; do not replace them with a general success label.
5. When a fix is retested, add the new evidence and tested version. Keep the original report and affected-version history. A passing result on a later version does not erase a v0.8.3 issue.

## Prioritizing follow-up work

Review reports as they arrive. Address lost/corrupted saves, crashes, incorrect hardware writes/readback, and unusable install paths first. Then address blocked workflows, unreliable telemetry, and inaccessible controls. Use repeatable before/after reports to choose the first v0.9 recommendation improvements.

The next v0.8.x release should list the specific issues it fixes and the configurations used to retest them. This tracker follows the roadmap's [public beta stabilization priority](../../ROADMAP.md); it is not a blanket certification of all listed hardware.
